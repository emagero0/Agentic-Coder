## Decision: Priority Routing Table for Event Tier Separation

**Date**: 2026-02-15
**Status**: Decided
**Owner**: Event System Team

### Context
The event system needed to handle three fundamentally different types of work: synchronous cache updates (fast, must succeed immediately), asynchronous dependency checks (medium, should complete), and deferred maintenance tasks (slow, best-effort). Early designs proposed using RabbitMQ or Bull for queue-based orchestration, but the operational overhead was out of proportion: there was no need for cross-process queues, persistence, or consumer groups in a single-process agent runtime.

### Decision
Replace queue-based orchestration with a **priority routing table** — a `Map<EventType, Handler[]>` with explicit tier labels (`sync | async | deferred`). Each tier maps to a simple handler array; the event dispatcher iterates handlers synchronously for Tier 1, async for Tier 2, and fire-and-forget for Tier 3.

### Rationale
The routing table pattern is simpler to implement, easier to debug, and has zero infrastructure dependencies. It covers 90% of the event use cases without the serialization, deserialization, and connection overhead of a message queue. Tier labels make the execution semantics visible at a glance in the handler registration code.

### Alternatives Considered
| Alternative | Pros | Cons | Why Rejected? |
|-------------|------|------|---------------|
| RabbitMQ / Bull queues | Persistent delivery, retry, dead-letter | Requires broker process, connection management, serialization overhead | Over-engineered for a single-process agent runtime; no cross-process need |
| Priority queue (array with sort) | Simple, in-memory | No tier isolation; a high-priority Tier 3 event could block Tier 1 | Tier isolation is a hard requirement; sorting alone is insufficient |
| Actor system (e.g. Orleans) | Built-in concurrency, fault tolerance | Heavy runtime, steep learning curve | Way too much infrastructure for a coordinator agent that runs inside OpenCode |

### Impact
**Positive**: Zero infrastructure dependencies. Dispatcher code is ~40 lines and trivial to unit test. Adding a new handler is a single `handlers.set(Tier, [...])` call.
**Negative**: No built-in retry for Tier 3 deferred events. If the process dies mid-handler, that work is lost. Tier 3 handlers must tolerate this.
**Risk**: As the event system grows, the routing table could become a bottleneck if all handlers for a tier are processed sequentially. Mitigation: keep handlers stateless and idempotent.

## Decision: Inferred/Verified State Split

**Date**: 2026-02-20
**Status**: Decided
**Owner**: State System Team

### Context
The cognitive platform produces two qualitatively different kinds of state: **inferred state** (generated by AI prompts, heuristic reasoning, or graph traversal — may contain hallucinations or errors) and **verified state** (confirmed by a human operator, validated by schema, or derived from an authoritative source). Without a clear split, inferred data could accidentally be promoted into verified state, creating downstream bugs that are hard to trace.

### Decision
Split the state management layer into two explicit partitions:
- **Inferred state**: Tagged with `source: 'inferred'`, stored in a separate path, and prefixed with `inferred/` in snapshot names. Cannot be queried by default in verified-state contexts.
- **Verified state**: Tagged with `source: 'verified'`, validated against a Zod schema before every write, snapshot-before-write enforced.

### Rationale
The split prevents a class of subtle bugs where AI-inferred data (e.g., "the user wants feature X based on a single chat message") gets treated as authoritative ("the user confirmed feature X"). By requiring an explicit promotion step (`inferred → review → verified`), the system forces human (or hardened deterministic) review before inferred data becomes ground truth.

### Alternatives Considered
| Alternative | Pros | Cons | Why Rejected? |
|-------------|------|------|---------------|
| Single state store with metadata tags | Single API surface | Tags are easy to forget or mis-set; no hard partition prevents accidental reads in verified context | Too easy to accidentally bypass the separation |
| Two separate databases/filesystems | Strong isolation | Duplicate infrastructure, migration complexity, query complexity | The state volume doesn't justify two databases; directory-level separation is sufficient |
| Immutable event log (event sourcing) | Full audit trail, no split needed | High storage cost, complex querying, over-engineered for current state volume | The platform does not need full event sourcing; snapshots are enough |

### Impact
**Positive**: Zero accidental promotions since deployment. The review gate (`inferred → verified`) is explicit and logged. Snapshots are easy to bucket into `inferred/` and `verified/` directories.
**Negative**: Every verified write requires schema validation, which adds ~5ms per write. Inferred state cannot be directly used by downstream systems that expect verified data.
**Risk**: The promotion step could be a workflow bottleneck if the team doesn't keep up with reviewing inferred state. Mitigation: batch promotion UI or CLI command (`opencode state promote <id>`).

## Decision: RuntimeAdapter Pattern for Runtime Abstraction

**Date**: 2026-01-25
**Status**: Decided
**Owner**: Platform Team

### Context
The OAC platform was initially built for Bun, taking advantage of Bun's fast startup, built-in test runner, and TypeScript support. However, the team wanted to keep the door open for Node.js and Deno deployments. Bun-specific APIs (Bun.file(), Bun.env, Bun.sleep, etc.) were scattered throughout the codebase, making a runtime switch a significant refactoring effort.

### Decision
Introduce a **RuntimeAdapter** interface that abstracts all runtime-specific operations. The interface defines methods for file I/O, environment variables, timers, subprocess spawning, and crypto. Every module that needs a runtime capability receives an adapter instance via dependency injection (constructor parameter). A `BunRuntimeAdapter` is the default implementation; stubs exist for Node and Deno.

### Rationale
The interface boundary makes runtime dependencies explicit and testable. Unit tests inject a `TestRuntimeAdapter` that uses in-memory primitives. Adding a new runtime target means implementing a single interface. The pattern is well-understood (similar to Go's `io.Reader`/`io.Writer` or Rust's trait patterns) and does not require a DI framework — plain old constructor injection suffices.

### Alternatives Considered
| Alternative | Pros | Cons | Why Rejected? |
|-------------|------|------|---------------|
| Keep Bun-specific calls inline | No abstraction overhead, simple code | Impossible to test without Bun runtime; switching runtimes requires touching every file | Lack of test isolation is a dealbreaker |
| Use a transpiler (e.g., Bun's `--target`) | Zero code changes | Locks into Bun's transpiler; doesn't help with API differences (e.g., `Bun.file` vs `fs.readFile`) | Transpilation only handles syntax, not API semantics |
| Publish `@opencode/runtime-adapter` as separate npm package | Clean separation, versioning | Package maintenance overhead, publish workflow, version drift | The adapter is small (~100 lines); internal is adequate |

### Impact
**Positive**: Full testability — every module can be tested with a `TestRuntimeAdapter`. Runtime targets are explicitly enumerated in a single file. Adding Node.js support is a matter of ~1 week of implementation work.
**Negative**: Every runtime-dependent module (currently ~25 modules) must accept an adapter parameter. This adds boilerplate, but the pattern is consistent.
**Risk**: The adapter interface could grow too large, making new runtime implementations burdensome. Mitigation: keep the interface focused on I/O primitives; higher-level abstractions (e.g., HTTP client) are not adapter concerns.

## Decision: MVI Context System (<200 Lines Per File)

**Date**: 2026-01-10
**Status**: Decided
**Owner**: Context System Team

### Context
The context system stores operational knowledge for OpenCode agents. Early drafts had large monolithic files (500+ lines) covering multiple topics. These files were hard to navigate: a developer looking for error-handling conventions had to scroll through architecture descriptions, setup guides, and deployment notes. Agents loading these files consumed excessive tokens.

### Decision
Adopt the **MVI (Minimal Viable Information)** principle: every context file must focus on exactly one purpose and stay under 200 lines. The function-based folder structure (concepts/ examples/ guides/ lookup/ errors/) enforces this by providing a clear home for each type of knowledge.

### Rationale
Small, focused files are scannable in under 30 seconds. They consume fewer tokens when loaded by an agent. The function-based structure makes it obvious where to add new knowledge. Cross-references between files are explicit (`Related Files` section), so no information is lost by splitting.

### Alternatives Considered
| Alternative | Pros | Cons | Why Rejected? |
|-------------|------|------|---------------|
| Large monolithic files | Everything in one place, fewer files | Hard to navigate, high token cost, poor scannability | Defeats the purpose of an agent-readable context system |
| Topic-based folder structure | Familiar to documentation writers | Topics overlap; a topic like "deployment" may contain both concepts and guides | Ambiguous where a piece of knowledge belongs |
| Wiki-style with hyperlinks | Rich cross-referencing, familiar | Not agent-friendly (agents struggle with link graphs), external dependencies | Context files must be self-contained for agent loading; external wiki breaks this |

### Impact
**Positive**: 100+ context files are all under 200 lines. New contributors report they can understand the full system in under 30 minutes by reading the top-level navigation.md and then drilling into relevant categories.
**Negative**: Cross-file navigation is manual (no graph view). When a concept spans multiple files, readers must follow cross-reference links.
**Risk**: Files could grow beyond 200 lines over time without enforcement. Mitigation: code reviews flag bloated files; automated size check via CI lint script.

## Decision: Snapshot-Before-Write for State Safety

**Date**: 2026-02-22
**Status**: Decided
**Owner**: State System Team

### Context
The state management system handles mutable state (context registries, skill configurations, audit snapshots). A write that corrupts or accidentally overwrites state could lose hours of agent work. The system had no recovery mechanism: if a write went wrong, the state was lost.

### Decision
Before every state mutation, the system writes a timestamped snapshot of the current state to a `snapshots/` directory. The write only proceeds if the snapshot is confirmed on disk. If a write fails or produces invalid state (per schema validation), the system rolls back by restoring the snapshot.

### Rationale
Snapshot-before-write provides a reliable, zero-cost (in developer time) safety net. It does not require a database, a transaction manager, or any external infrastructure — it uses the filesystem with atomic rename operations. The ISO-8601 timestamp naming convention makes snapshots trivially sortable and cleanable.

### Alternatives Considered
| Alternative | Pros | Cons | Why Rejected? |
|-------------|------|------|---------------|
| Database transactions (SQLite) | Atomic commits, rollback, ACID | Adds SQLite dependency, connection management, query overhead | Over-engineered for snapshot-based state; filesystem snapshots are sufficient |
| WAL (write-ahead log) | Full recovery, no data loss | Complex implementation, replay logic, storage growth | Snapshot-before-write is simpler and covers the rollback use case |
| Immutable data structures (persistent data structures) | No mutation = no corruption | Memory overhead, not natural for filesystem-backed state | Harder to reason about with TypeScript and JSON serialization |

### Impact
**Positive**: Zero data loss incidents since deployment. The rollback mechanism has been triggered 3 times during development (all due to edge cases in state migration code), and each time the snapshot was successfully restored.
**Negative**: Snapshot storage grows unbounded. A TTL-based cleanup policy is needed but not yet implemented. Dev environments can accumulate GB-scale snapshot directories.
**Risk**: If both the current state file and the snapshot are corrupted (e.g., filesystem failure), recovery is impossible. Mitigation: planned feature to keep the last N snapshots and replicate critical snapshots to a backup directory.
